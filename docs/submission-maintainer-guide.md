# Submission acceptance and validation

1. Check required fields and confirmations against the current form. Run `python scripts/check_submission_completeness.py --event issue-event.json` on a saved GitHub event (or issue API JSON). This is read-only; no record is created, posted or approved. Optional fields are not acceptance blockers. Scientific scope, valid links and attribution still require review.
2. Preserve the original issue, submitter and consent. Community Tools can be accepted as unreviewed stubs; Strategies retain their methodological inclusion criteria. Never invent consent or claim editorial review from field completeness alone.
3. Review the generated change, then require the PR's `validate` check to succeed on the current main base. A successful standalone/manual workflow is not proof that the protected PR requirement is satisfied.
4. If the bot-created PR has no running check, inspect Actions for an approval-required run and approve it only after reviewing its source. GitHub's current documentation describes approval-required runs for bot-created pull requests. If no run exists, a maintainer can close/reopen the still-open PR (after checking its review history) to generate a real PR event. Do not reopen intentionally rejected PRs without a decision to reconsider.
5. If main has advanced, update the PR branch and wait for validation again. Merge only after required checks pass. The generated PR includes a closing reference to its original issue.

## Recovery without overwriting editorial work

The automation recognizes a submission marker anywhere in the title, or its form label. Conflicting Tool/Strategy markers fail explicitly. Existing automation branches are never force-pushed or regenerated by a rerun: inspect their existing PR and preserve manual edits. Editing an issue does not automatically overwrite its existing draft. For older missed submissions, run the completeness check, generate the record in a separate branch with the existing converter, inspect it and open a recovery PR referencing the original issue.

## Limits and remaining work

This patch is not deployed until its draft PR is accepted. It does not grant new token permissions, automatically approve workflow code, bypass branch protection or guarantee unattended validation. Live GitHub approval behavior needs a real submission smoke test after an approved rollout; local tests only validate detection and field handling.
